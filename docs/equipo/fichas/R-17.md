**Cómo se usa.**

```
active-stack memory init [--project <ruta>] [--name <nombre>] [--yes] [--json] [--lang en|es]
```

Sin `--name` ni `--yes`: en una terminal pregunta si usar el nombre calculado; sin terminal sale con código `3` mostrando el nombre y cómo confirmarlo. No escribe nada hasta que el nombre esté confirmado.

**Orden de ejecución.** (1) resuelve la raíz Git; (2) calcula el nombre; (3) lee y planifica los tres archivos (un conflicto o un JSON inválido corta acá, sin escribir); (4) la persona confirma el nombre; (5) avisos de solo lectura; (6) backup de los archivos que ya existían y van a cambiar (si falla, no toca nada); (7) escribe `.engram/config.json`, `.engram/active-stack.json`, `.gitignore`; (8) le pregunta a Git, con `check-ignore --no-index`, que los dos archivos sean versionables y que el resto de `.engram/` esté ignorado, y si no, **devuelve todo**; (9) **imprime** el commit propuesto.

**Códigos de salida.** `0` listo o ya al día · `1` error (sin Git, no es un repo, JSON inválido, falló el backup o una escritura, raíz = carpeta personal) · `2` uso incorrecto · `3` se detuvo para no pisar algo de la persona, o falta confirmar el nombre.

**`--json`.** Siempre las diez claves: `status` (`ok` | `needs_decision` | `error`), `reason`, `root`, `project_name`, `name_source`, `files`, `backup_dir`, `warnings`, `proposed_commit`, `detail`. Los motivos: `conflict_value`, `conflict_ignored_dir`, `conflict_still_ignored`, `conflict_not_ignored`, `name_not_confirmed`, `name_declined`, `invalid_file`, `backup_failed`, `home_directory`, `not_git_repo`, `empty_name`, `git_missing`, `failed`. Es lo que va a leer R-19.

### El commit que propone

```
git add -- .engram/active-stack.json .engram/config.json .gitignore
git commit -m "chore(engram): pin project and team memory policy" -- .engram/active-stack.json .engram/config.json .gitignore
```

La lista es la de los archivos que **Git todavía ve como pendientes** (cambiados o sin versionar), no solo los que esta corrida tocó: si la persona corre `init` y recién después commitea, una segunda corrida sigue mostrando lo que falta. Cuando todo está commiteado dice «nada para commitear». Dos avisos que no frenan: (a) un archivo ya versionado tenía cambios **sin commitear de la persona** (el commit propuesto los incluiría); (b) hay otros archivos de `.engram/` ya versionados (el `.gitignore` no los des-versiona).

## Lo que ya se sabe (no se vuelve a medir)

- Q10 (piloto, [evidencia](../../research/engram-cloud-piloto-2026-11-19.md)): con `project_name` en `.engram/config.json`, el checkout, un clon y un worktree eligen el mismo proyecto. Sin él, el worktree sigue coincidiendo con el checkout (ambos salen de la raíz de Git) pero **un clon elige otro** (`unknown`, por el remoto). Es la razón de ser de este comando: unir los clones. Es la razón de ser de este comando.
- **R17-D, medido** ([sonda](../../research/r17-nombre-proyecto/sonda_nombre.py), [resultado](../../research/r17-nombre-proyecto/resultado-engram-3.7.1.txt); Engram 3.7.1, `mem_current_project`, base en una carpeta temporal y `HOME` aislado; la base real no se tocó): con `project_name` = `Mi-App` Engram detecta `mi-app`; `Proyecto-Ñandú` → `proyecto-ñandú`; `MAYUSCULAS_con_guion_bajo` → `mayusculas_con_guion_bajo`; `mi repo con espacios` queda igual. La fuente es `config` en todos. Es decir: Engram baja todo a minúsculas (también Unicode) y no toca los espacios. **No se midió** cómo compara el servidor `ENGRAM_CLOUD_ALLOWED_PROJECTS` (con mayúsculas o sin ellas) ni si 3.7.2 se comporta igual (R-05 usó 3.7.2; esta máquina tiene 3.7.1).
- La documentación de Engram solo describe `project_name` en `.engram/config.json`; las claves extra y si se toleran: no documentado ([EN] sección 2.2). Por eso el marcador es un archivo propio.
- R-15 y `memory branch` ya leen `.engram/active-stack.json` y aceptan CRLF y BOM (R08-5). `memory init` escribe LF y sin BOM en lo que crea.
