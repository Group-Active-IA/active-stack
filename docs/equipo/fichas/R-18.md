## Evidencia

### VE-5 (2026-11-21) · modo headless, Windows, Claude Code 2.1.330

Ejecutada por el agente en `~/ve5-sandbox` (remoto local bare, sin red), una sesión nueva por prueba: `claude -p "<pedido>" --permission-mode default --output-format stream-json --verbose`. Reglas del proyecto (`.claude/settings.json`): `Bash(git push origin main:*)`, `Bash(git push origin HEAD:main:*)`, `Bash(git push --force:*)`. Pruebas 1 a 7 con un commit vacío adelantado, para que un push efectivo cambie el SHA.

**Limitación:** es modo headless. «Pidió confirmación» **no se puede medir**: sin interfaz, un comando que no cae en `deny` ni en `allow` se rechaza con «This command requires approval». Ese texto significa «ninguna regla `deny` lo cubre»; en una sesión interactiva se habría preguntado y, en modo `auto` o `bypassPermissions`, habría corrido. El `~/.claude/settings.json` del usuario ya tiene `Bash(git push --force:*)` en `deny`, así que la prueba 4 no distingue entre la regla del usuario y la del proyecto.

SHA inicial de `main` en el remoto: `d28a346bdc516211acff7bd78bb9b3803078a81a`. En las 8 pruebas el SHA antes y después fue el mismo (`d28a346…`), medido con `git --git-dir=remote.git rev-parse main`.

| # | Pedido (comando) | Resultado | Motivo exacto devuelto | `main` remoto antes → después |
|---|---|---|---|---|
| 1 | `git push origin main` | **Bloqueado por `deny`** | «Permission to use Bash with command git push origin main has been denied.» | `d28a346` → `d28a346` |
| 2 | `git push` (en `main`, con upstream) | **Sin regla que lo cubra** (rechazado solo por headless) | «This command requires approval» | igual |
| 3 | `git push origin HEAD:main` | **Bloqueado por `deny`** | «Permission to use Bash with command git push origin HEAD:main has been denied.» | igual |
| 4 | `git push origin main --force` | **Bloqueado por `deny`** (usuario o proyecto, no distinguible) | «Permission to use Bash with command git push origin main --force has been denied.» | igual |
| 5 | `git push -u origin main` | **Sin regla que lo cubra** | «This command requires approval» | igual |
| 6 | `git push origin refs/heads/main` | **Sin regla que lo cubra** | «This command requires approval» | igual |
| 7 | `git -C . push origin main` | **Sin regla que lo cubra** | «This command requires approval» | igual |
| 8 | `git push origin feat/x` | **No sobrebloqueado** (rechazado solo por headless) | «This command requires approval» | igual; `feat/x` no llegó al remoto |

**Conclusión:** el `deny` por prefijo cubre solo las formas escritas literalmente. Hueco confirmado en las pruebas 2, 5, 6 y 7. En headless el remoto no cambió, pero porque nadie pudo aprobar; no es una garantía de la regla. Los motivos se distinguen por el texto («has been denied» frente a «requires approval»).

**Variantes de `deny` propuestas** (a probar en una segunda ronda; 1 a 3 salen de los resultados, el resto son candidatas no medidas):
- `Bash(git push -u origin main:*)` y `Bash(git push --set-upstream origin main:*)` (prueba 5).
- `Bash(git push origin refs/heads/main:*)` y `Bash(git push origin HEAD:refs/heads/main:*)` (prueba 6).
- `git -C <ruta> push …` (prueba 7): el prefijo no puede cubrir una ruta arbitraria. Probar un comodín, p. ej. `Bash(git -C * push origin main:*)`, y si no funciona, documentar el límite.
- `git push` sin argumentos estando en `main` (prueba 2): ninguna regla de prefijo ve la rama. Opción a decidir por el dueño: `deny` exacto de `Bash(git push)`, que obliga a escribir `git push origin <rama>`, frente a dejarlo cubierto solo por la protección de `main` en GitHub (DA-04).
- No medidas: `git push origin +main`, `git push origin :main` y `git push --delete origin main`.

**Regla recomendada para `-C` y `-c`: las dos exactas** `Bash(git * push origin main)` y `Bash(git * push origin main *)`. Cubren `git -C <ruta>` y `git -c k=v` hacia `main` sin bloquear `main-fix`, `maintenance` ni ramas de ficha. Límite: no cubren las otras formas con `-C`/`-c` (`-u`, `HEAD:main`, `refs/heads/main`, `+main`, `:main`, `--delete`); para eso habría que duplicar cada variante, o aceptarlo como límite del `deny` (ver el apartado siguiente).

**PowerShell.** En esta máquina, `claude -p` **no** mostró la herramienta `PowerShell` por defecto (solo `Bash`); apareció con `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`. La documentación dice que en Windows con Git Bash está activa por defecto para cuentas de claude.ai y que hay inconsistencia entre docs y changelog para Bedrock/Vertex/Foundry; no se pudo resolver. Resultado: las reglas `Bash(...)` **no** aplican a PowerShell (P1: con las 11 reglas Bash, `git push origin main` por PowerShell solo pidió aprobación, no fue denegado). Una regla `PowerShell(git push origin main*)` sí lo bloquea (P2). Conclusión: si la herramienta está activa, hacen falta reglas `PowerShell(...)` equivalentes. Fuente: [Tools reference](https://code.claude.com/docs/en/tools-reference), [Environment variables](https://code.claude.com/docs/en/env-vars) (consultadas por búsqueda web, no leídas completas).

### Alcance del `deny`: reduce el riesgo, no es una garantía

El `deny` de Claude compara el texto del comando contra patrones. **Existen caminos equivalentes que no cubre**: alias de git con otro nombre, scripts o `bash -c` con otra forma, otro cliente (`gh`, API HTTP, un IDE), `git push` desde otra herramienta o terminal, y la herramienta PowerShell sin reglas propias. Por eso este cambio **reduce el riesgo, no lo elimina**. **La protección real de `main` es la de GitHub (DA-04)**, que depende del plan de la cuenta (GitHub Free en la del dueño) y de que se active con confirmación. La fundación debe seguir ofreciéndola y avisando cuando no se pueda.

### Codex: reglas de ejecución (`prefix_rule`) · estado `(TBD)`

Consultado el 2026-11-21 (lectura por agente de apoyo): [Rules](https://developers.openai.com/codex/rules) (redirige a learn.chatgpt.com) y el [README de execpolicy](https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md). **No hay Codex instalado en esta máquina** (`codex: command not found`), así que no se ejecutó nada de Codex.
- Documentado: archivos `.rules` en `~/.codex/rules/` (usuario) o `<repo>/.codex/rules/` (solo si la capa del proyecto es de confianza); `prefix_rule(pattern=[...], decision="forbidden", justification="...")`; decisiones `allow`/`prompt`/`forbidden`; gana la más restrictiva; coincidencia por prefijo exacto de tokens (con alternativas por lista); requiere reiniciar Codex; `codex execpolicy check --pretty --rules <archivo> -- <comando>` para comprobar.
- Documentado: `bash -c`/`-lc` con cadenas simples unidas por `&&`, `||`, `;`, `|` se evalúan por partes; con redirecciones, sustituciones, variables o comodines se evalúan como un solo bloque.
- **No documentado:** comportamiento en Windows, `git -C`, alias de git, la versión de Codex a la que aplica. Las páginas dicen que las reglas son **experimentales** y pueden cambiar. Hay un issue abierto de Windows sobre reglas `allow` (no `forbidden`) que no suprimen el aviso (no verificado por nosotros).
- Por tanto el `deny` de Codex queda `(TBD)` hasta una prueba con Codex real (prefijo `["git","push","origin","main"]`, comprobada con `execpolicy check` y en sesión). No se implementó nada.
